## Reglas de Desarrollo

### Archivos que NO se deben modificar
- Todo dentro de `assets/vendor/` — Son librerías de terceros
- `LICENSE` — Licencia del template

### Estilos (CSS)
- **Editar solo `assets/css/main.css`**, nunca los CSS de vendor
- Usar las **CSS custom properties** existentes para colores:
  - `--background-color`, `--default-color`, `--heading-color`, `--accent-color`, `--surface-color`, `--contrast-color`
  - Colores de navegación: `--nav-color`, `--nav-hover-color`, `--nav-dropdown-*`
- Las clases de contexto de color son: `.light-background`, `.dark-background`, `.accent-background`
- Las fuentes se controlan con: `--default-font` (Roboto), `--heading-font` (Raleway), `--nav-font` (Poppins)
- Los estilos están organizados por sección con comentarios delimitadores `/* ------ # Sección ------ */`
- Mantener la convención de BEM ligero usada en la plantilla (ej: `.resume-item`, `.info-item`, `.skills-content`)
- Usar `color-mix()` para variaciones de color como ya hace el template
- **Principio DRY**: Si un estilo se repite en 3+ secciones, considerar abstraerlo a una clase utilitaria
- **Especificidad baja**: Preferir clases sobre selectores anidados profundos — menor especificidad = mayor mantenibilidad

### JavaScript
- **Editar solo `assets/js/main.js`**
- El código está envuelto en un **IIFE** `(function() { "use strict"; ... })();`
- Mantener ese patrón. No añadir código fuera del IIFE — esto aplica el **principio de encapsulación**: el scope global no se contamina
- Usar **vanilla JS** (no jQuery) — consistente con el código existente y con el estándar moderno de la plataforma web
- Las inicializaciones de librerías se hacen en `window.addEventListener('load', ...)`
- Para nuevas animaciones, usar la función `aosInit()` ya existente o atributos `data-aos`
- **Separación de responsabilidades**: Cada bloque de funcionalidad (scroll, typed, isotope, swiper) está claramente delimitado con comentarios. Mantener esa organización al añadir código nuevo
- **Fail gracefully**: Validar existencia de elementos antes de operar (`if (element) { ... }`), como ya hace el template con `selectTyped` y `preloader`
- **Event delegation**: Para elementos repetidos o dinámicos, preferir delegar eventos en un padre común sobre añadir listeners individuales

### HTML
- Seguir la estructura de secciones existente: `<section id="nombre" class="nombre section [background-class]">`
- Cada sección tiene un título opcional con: `<div class="container section-title">`
- Usar clases de Bootstrap 5 para layout (`row`, `col-lg-*`, `gy-4`, etc.)
- Usar `data-aos` y `data-aos-delay` para las animaciones de entrada
- Los iconos se aplican con clases `bi bi-[nombre]` (Bootstrap Icons)
- Los enlaces del portfolio usan filtros Isotope con `data-filter`
- **HTML semántico**: Usar las etiquetas correctas por su significado (`<article>`, `<nav>`, `<main>`, `<footer>`), no solo por su apariencia. Esto mejora accesibilidad y SEO
- **Principio de mínima sorpresa**: La estructura de una nueva sección debe seguir exactamente el mismo patrón que las existentes — quien lea el código debe poder predecir la estructura

### Imágenes
- Guardar imágenes del portfolio en `assets/img/portfolio/`
- Guardar imágenes de testimonios en `assets/img/testimonials/`
- Otras imágenes generales en `assets/img/`
- Optimizar imágenes antes de añadirlas (formatos: WebP preferido, JPG/PNG aceptables)

## Buenas Prácticas

### Accesibilidad (WCAG 2.1)
- Mantener atributos `alt` descriptivos en imágenes (no decorativas: `alt=""`)
- Preservar `aria-*` en barras de progreso y elementos interactivos
- Contraste de color mínimo 4.5:1 para texto normal, 3:1 para texto grande
- Navegación por teclado funcional en todos los elementos interactivos
- Estructura de headings jerárquica (`h1` → `h2` → `h3`, sin saltar niveles)

### SEO
- Actualizar `<title>`, `<meta description>`, `<meta keywords>` en el `<head>`
- Un solo `<h1>` por página
- URLs de imágenes descriptivas (ej: `proyecto-ecommerce.webp` en vez de `img1.jpg`)
- Texto alternativo en imágenes relevantes para buscadores

### Performance (Core Web Vitals)
- Usar versiones `.min.css` y `.min.js` de vendors (ya configurado)
- Optimizar imágenes: WebP cuando sea posible, dimensiones adecuadas (no escalar con CSS una imagen de 4000px)
- Atributo `loading="lazy"` en imágenes below-the-fold
- Minimizar reflows: definir `width` y `height` en imágenes para evitar layout shift (CLS)

### Responsive Design
- El template es **mobile-first** con Bootstrap — testear siempre en viewport móvil
- No usar valores fijos de `px` para anchos de contenedores; usar el grid de Bootstrap
- Verificar que el menú móvil (hamburguesa) funcione correctamente tras cambios en la navegación

### Principios de Ingeniería Aplicados
- **DRY** (Don't Repeat Yourself): Si repites markup o estilos, abstrae a un patrón reutilizable
- **KISS** (Keep It Simple, Stupid): Este es un sitio estático — no sobreingeniería. Si no necesitas un framework JS, no lo añadas
- **Separación de responsabilidades**: HTML = estructura, CSS = presentación, JS = comportamiento. No mezclar estilos inline ni lógica en el HTML
- **Open/Closed (adaptado)**: Las secciones existentes deben poder extenderse (añadir contenido) sin modificar la estructura base del template
- **Progresive Enhancement**: El contenido debe ser accesible sin JS. Las animaciones (AOS, Typed.js) son mejoras progresivas, no dependencias

### Control de Versiones
- Commits descriptivos en español, separando contenido de estructura
- Un commit por cambio lógico (no mezclar "cambié mi nombre" con "añadí nueva sección")
